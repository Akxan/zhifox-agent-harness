# 会话

## 会话是怎么保存和恢复的

模型自己什么都不记得，"接着上次聊"靠的全是 harness：把上次的对话历史存下来，下次请求时一起发过去。
每段会话是 `data/conversations/` 里的一个 JSON 文件，里面有两份内容：

| 内容 | 给谁用 | 说明 |
|---|---|---|
| `messages` | 模型 | 发给模型的对话历史，按那一家的格式原样保存。打开会话时交还给适配层（`restore`） |
| `events` | 页面 | 界面上显示过的内容。打开会话时重新发给浏览器，页面照着画出来 |

两种界面存的是同一种文件，存法也一样：每一轮结束存一次。终端自己用不着 `events`（屏幕上的字打出去就完了），
但它照样记一份，用的就是网页那个类（[webui/ui.py](../../harness/webui/ui.py) 的 `WebUI`），存之前也是同样地整理。
所以终端里聊的会话在网页上打开，看起来就像是在网页上聊的：你的消息、照 Markdown 画出来的回答、工具卡片、确认和结果、
运行记录、"改了 N 个文件"那一行。只记一轮里显示的内容：终端自己的命令（`/help`、`/usage`……）不算对话的一部分。

附件在 `events` 里只有一份概要：名字、大小、一张小缩略图，和它的原件在 `data/media/` 里的编号（内容的 SHA-256）。
完整的内容在 `messages` 里（模型读的是它），也在多媒体库里。多媒体库的索引和搜索一样，是在读入、保存会话的时候顺手建的，
所以打开"多媒体"不用把所有会话文件再读一遍。

存两份是因为它们不一样：模型看到的历史里有思考内容的签名、每个工具调用的编号、厂商各自的消息结构，
这些页面用不上，但发回给 API 时一个字都不能差；页面上显示的确认卡片（你点了允许还是拒绝）、
"已中断"这样的提示文字，又是模型看不到的。

Claude 的历史必须和当初一字不差地发回去，否则它之前的思考内容通不过校验。如果你换了工作目录再打开旧会话，
系统提示词已经变了，那些思考内容就对不上了。程序在请求里带了一个参数，让 API 遇到这种情况时丢掉对不上的思考内容，
而不是拒绝请求，所以旧会话仍然能接着聊，只是模型看不到自己当时是怎么想的。

## 编辑最后一条消息、重新生成

两件事是同一个动作：把对话倒回去一点，再跑一遍。"重新生成"倒到你最后一条消息之后：这条消息原样留着，
连同当时的时间说明和附件，所以新的请求开头和上一次一字不差（缓存照样命中）；模型这一轮做的（思考、回答、
工具调用和它们的结果）全部去掉。"编辑"倒到你最后一条消息之前，把改过的那条当作新的一轮发出去。

只能倒最后一轮，因为对话历史只在末尾追加（见[循环](architecture.md#循环)）。改了中间的某一轮，它后面的缓存全部作废；Claude 后面的每一块
思考内容都带着签名，签名绑着它前面的全部内容。从末尾去掉一截，留下的每一块前面的内容都不变。

倒到哪儿：每一轮开始时，网页界面（终端也一样）把适配层在历史里的位置（`Backend.mark()`）记在这一轮的 `user` 事件上，跟着会话一起存下来，
所以不管会话是在哪边聊的，终端里的 `/retry`、`/edit` 和网页上的"重新生成""编辑"都能用。
GPT、Gemini、DeepSeek 的位置从对话开始数，被压缩掉的也算在内；会话文件里另外记着压缩掉了多少条（`dropped`），
所以重新打开、重启之后，记下的位置照样对得上。倒回去之前先问适配层：这个位置上还是不是这一轮的那条用户消息（`Backend.turn_at`）：

- 是：就倒到这里。
- 不是，而历史正好到这里为止：这一轮在模型答出第一步之前就失败了，消息已经撤回（页面上还看得到它）。
  "重新生成"就是再发一次，附件从多媒体库里取回原件。
- 不是，后面还有：这一轮已经压缩进了摘要，倒不回去，按钮上写着为什么。这个功能之前存的会话、定时任务自己跑的那一轮
  （发给模型的指令和页面上显示的不一样）也倒不回去。

做过的事撤销不了：倒回去的只是对话。这一轮执行过命令、改过文件、调用过 MCP 工具、操作过整台电脑、在浏览器里点击或输入过
（自己做的、交给子 Agent 做的都算），页面会把这些事列出来问你一次。操作过整台电脑、浏览器的，确认里另外单独写一句：
在别的程序里做过的、在网页上已经提交和发出去的，撤不回来。只是"看"的不算（截图、读页面、打开一个网址；整台电脑那边只有截图、
放大看、问鼠标在哪儿、等一会儿算"看"）。你拒绝了的不算；智狐自己的待办、文件、记忆、定时任务工具出错了的也不算：
它们先把一切查好才写，出错就是什么都没改。认不出来的工具一律算"可能改动了什么"。

花掉的钱：已经花了就是花了。花费账本一笔不少地留着，信息栏里这段对话的用量和费用也不减；上下文的大小等下一次请求时更新。

页面上：服务器把历史和保存的事件一起截断，马上存一次盘（搜索和多媒体库跟着更新），再发一个 `reset`、把留下的事件重放一遍，
和打开一段会话是同一个做法。开着的每个标签页都原地重画，不用刷新。请求里写明是哪段会话的哪一轮，落后的标签页会被拒绝，
不会倒回别的内容；正在改的标签页，没发出去的字会放回它的输入框。

## 从某一轮分叉

倒回只能倒最后一轮。想"从第 3 轮换个思路重来"，就从那一轮分叉：原来那段一个字节都不动，新开的一段从那里接着聊。
每一轮结束以后，这一轮上有两个"分叉"：

- 回答下面那排按钮里、紧挨着"复制"的"从这里分叉（带上这一轮）"：新的一段里是到这一轮结束为止的全部内容，接着说就是新的方向。
- 鼠标移到你的消息上，左边的"从这条消息分叉（改了再发）"（最后一条消息上排在"编辑"左边）：新的一段截到这一轮开始之前，
  这条消息（文字和附件）放回输入框，改了再发。在第一条消息上分叉，新的一段是空的，和新对话一样，第一轮结束才存盘。

点了以后直接换到新的一段。它的标题后面带着"（分叉）"，会话栏里前面有一个小小的分叉图标，顶上一行写着从哪儿来的；
点"打开原会话"回到原来那段、滚到分叉的那一轮（原会话删掉以后，这一行只剩文字）。

为什么不违反"只追加"：两段历史都没有被改。新的一段的 `messages` 是原来那段的前缀，切在某一轮的开头，和倒回最后一轮是同一件事：
留下的每一块，它前面的内容都和当初一字不差，缓存照样对得上，Claude 思考内容的签名照样通过校验。
它用同一家的同一个模型、同一个角色（自定义 Agent）接着聊，之后照常只在末尾追加。

切在哪儿（[harness/fork.py](../../harness/fork.py)）：用的是 `user` 事件上记着的位置（见上一节）。在消息上分叉切在这一轮自己的位置，
在回答上分叉切在下一轮的位置（最后一轮就是整段历史）。这个位置还是不是一轮的开头，交给适配层自己的规矩去认
（`providers.saved_before`，和 `Backend.turn_at` 是同一笔账）。GPT、Gemini、DeepSeek 的历史压缩过：切口落在已经写进摘要的那一段，
和倒回一样分不了，那几轮的按钮是灰的、写着为什么；切口在摘要之后的，新的一段带着摘要，`dropped` 原样带过去，
所以它的事件里记着的位置也对得上（新的一段里照样能编辑、重新生成最后一轮）。没有记下位置的那一轮（定时任务自己跑的、
旧版本存下的）不能在那里分叉。`events` 截到同一个位置，这一轮的运行记录、子 Agent 的卡片、确认请求跟着这一轮走。

不跟过来的：改文件的记录（"改了 N 个文件"那一行和撤回、重做）不复制。留底（`data/backups/turns/`）按一轮的编号存，
磁盘上的文件也只有一份：两段会话都能撤回同一轮的话，一边撤回了，另一边那一行还写着"没撤回"，两边就对不上了。
所以撤回只在原会话里做；那几轮改过文件的，新的一段顶上那一行会说一句。从定时任务、聊天通道的会话分叉出来的，
是一段普通的网页会话（不带 `task`、`channel` 的标记），所以也没有 `send_file`。花掉的钱照旧；新的一段的上下文大小按它最后一轮的运行记录估。

页面上：分叉会换到另一段会话，所以要等你自己的这一轮结束。原会话只是读：从磁盘读（拿着会话库的锁，读不到写了一半的文件），
不认领它，所以聊天通道正在用的会话也能分叉。请求里写明是哪段会话的哪一轮，落后的标签页会被拒绝。
分叉只在网页界面里有；终端里存下的会话，在网页上和别的会话一样能分叉。

## 撤回一轮改的文件

倒回对话撤回的是对话，这里撤回的是文件。文件工具新建、修改、覆盖过文件的那一轮，末尾有一行"改了 2 个文件 +7 −1"，
右边的"撤回"一下撤回这一整轮。点开是每个文件（新增、修改还是覆盖，加了几行、删了几行）；点文件名看这一轮对它做了什么
（一行一行的预览），可以一个个撤回，也可以"撤回这一轮的全部改动"。"重做"把撤回时换下来的放回去。终端里输入 `/undo`，
先把最近一轮的改动列出来，问你一句再撤回。终端也存同样的 `file_changes`、`file_undo` 事件，所以终端里的一轮在网页上也有那一行，
`/open` 打开的会话，`/undo` 也认得它以前的改动。

怎么记下来（[harness/undo/](../../harness/undo/)）：一轮开始时，网页界面和终端为它开一本账；文件工具每次写之前问一句"有没有在记账"
（[tools/files.py](../../harness/tools/files.py) 里只有一行），这一轮第一次碰到一个文件时，先把它原来的样子留一份底（本来不存在就记下"不存在"），
存在 `data/backups/turns/<编号>/` 里，改完再记下这一轮把它改成了什么样。账记在这一轮的线程上（`ContextVar`）：你的对话、定时任务、
聊天通道是同时跑的，共用一个文件工具，只有你的对话那几轮记账（交给子 Agent 做的也算，它在同一个线程里跑）。一轮结束时写一份清单，
之后不再改，会话的事件里多一个 `file_changes`；发给模型的历史（`messages`）一个字都不动。几道上限在 `config.py` 里：
一个文件 10 MB，一轮 50 MB、100 个文件，留 30 天。超了的文件照样改，只是撤不回来，那一行上写着为什么。

不记的：`run_command` 改的文件。一条命令改了什么看不到：`sed -i`、`git checkout`、`npm install`、一个脚本……要看清楚，
只能在每条命令前后把整个工作目录拍一遍，大的项目里又慢又占地方，命令还能改工作目录之外的东西。所以那一行里明说
"命令改动的文件没法自动撤回"，这一轮执行过命令时写得醒目一些。智狐也不替你的仓库做 git 快照：那会在你的 stash、提交记录里留下东西，
和你正在做的 rebase、暂存区搅在一起，被忽略的文件照样撤不回来，还要每台电脑上都有 git。用 git 的话，自己提交一次就是最可靠的撤回点。

撤回和重做（[restore.py](../../harness/undo/restore.py)）：撤回把每个文件恢复成这一轮之前一字节不差的样子（连同权限），
这一轮新建的文件删掉（为它新建、现在空了的文件夹也删掉）。撤回之前先把文件现在的样子留一份底，"重做"就是把它放回去。写之前先逐个查一遍：

- 后来又被改过没有：按内容的哈希比（不看修改时间）。这一轮之后它又被改过（后面的一轮、你自己、别的程序），或者这段对话里后面的几轮也改过它，
  就在原地说清楚（后面的几轮改过的，说明撤回的是"这一轮之前"的样子，后面那几轮对它的改动也会一起没了），等你点"仍然撤回"。
  工作目录之外的、智狐自己的数据目录里的文件也一样先问。
- 永远不写：保存密钥、权限设置的那几个文件（和文件工具同一份名单）、留底的文件夹本身、后来换成了链接的路径（撤回只写当初记下的那个位置）、
  不见了或者对不上哈希的留底。

查和写拿着文件工具的同一把锁，别的对话、定时任务插不进中间。撤回只有你能做：网页上的按钮、终端里的 `/undo`，模型没有能撤回的工具。
每一次撤回、重做本身也是一个事件（`file_undo`），跟着会话存下来、刷新时重放：每个文件现在是什么状态由这些事件推出来，
清单只记这一轮做了什么。一件事只记在一处。

告诉模型：模型记得它改过的文件是什么样子。撤回以后，它要么 `str_replace` 找不到原文，要么照着记忆把整个文件重写一遍，
把撤回的又写了回去。所以这段对话的下一条消息前面附一小段 `<file_changes>`，列出撤回、重做了哪些文件，请它用到之前先重新看一眼。
它和时间、Skill 目录一样附在消息里，系统提示词和历史都不变；那条消息留在历史里了才算说过；接着又把那一轮倒回去的，关于它的那几句就不说了
（模型本来就没见过那一轮）。

和倒回对话一起用：最后一轮改过文件时，倒回去的确认卡片上有"同时撤回这一轮改的 N 个文件"（默认不勾）。勾上就先撤回文件；
有文件在这一轮之后又被改过，卡片上先说清楚，按钮换成"仍然撤回并重新生成"。最后一轮之后才撤回的更早几轮的改动，倒回最后一轮时不会跟着丢掉。

## 会话搜索是怎么做的

搜索要解决两个问题：找得快，找得到。代码都在 [harness/search.py](../../harness/search.py) 里，没有用任何搜索库。

找得快：不能每敲一个字就把所有会话文件重新读一遍。第一次用到会话列表或搜索时，程序要把每个会话文件读一遍来列出标题，
这时顺便把里面值得搜的文字抽出来放在内存里，这就是"索引"（终端版用不到会话列表，所以从来不建）。之后会话保存、改名、删除时索引跟着更新，
搜索只在内存里进行。

收进索引的有：标题、你说的话、助手的回复、思考过程、每次工具调用的那一行摘要（运行的命令、读写的文件路径、
联网搜索的关键词）、每个工具结果开头的 600 个字符。没有收的：助手写进文件的具体内容、出错和"已中断"这类提示。

找得到：人记得的往往只是个大概，所以匹配分五档，越严格的排得越靠前：

| 档 | 规则 | 例子 |
|---|---|---|
| 原样包含 | 关键词原样出现。不分大小写，全角半角算一样 | `HARNESS` 找到 `harness` |
| 相近的词 | 5 个字母以上的英文单词允许敲错一两个字母。只在这个词哪儿都原样找不到时才启用 | `hraness` 找到 `harness` |
| 隔字包含 | 每个字按顺序都出现，中间可以隔几个字。英文要 4 个字母以上，而且不跨单词 | `周五报告` 找到"周五下午交报告" |
| 全拼 | 字母拼成的关键词按拼音对汉字：至少两个完整的音节，对上挨在一起的几个字。不分大小写、不管声调，音节之间可以有空格或隔音符号；多音字的每个读音都算 | `baogao`、`bao gao`、`BaoGao` 找到"报告"；`yinhang` 找到"银行"，`xingzou` 找到"行走"（"行"两个音都算） |
| 首字母 | 每个字母是一个字拼音的第一个字母（zh、ch、sh 只算 z、c、s）。至少 3 个字母，只在标题里找 | `zbmb` 找到标题是"周报模板"的会话 |

多个关键词要全部满足，先后顺序不限，也可以分别出现在不同的地方。排序时先看档：每个关键词都原样找到的排最前，
其次是靠"相近的词"找到的，然后是用到"隔字包含"的、靠拼音找到的，用到"首字母"的排最后。同一档里，标题里的命中排在内容里的前面，
你说的话排在工具输出前面；一样相关时新的会话在前。

拼音：很多人用拼音输入法打字，在搜索框里敲 `baogao` 比切换输入法再选字快。可一串字母也可能是英文词，
所以拼音的两档要管得严，有这么几条规矩：

- 和"相近的词"一样，只在这个关键词哪儿都原样找不到时才按拼音试。`name` 拆得成 na + me（"那么"，到处都有），
  可要是有会话里原样写着 `name`，你找的就是这个英文词。
- 排在原来三档的后面：原来找得到的会话一个不少、先后不变，按拼音找到的只是接在后面。
- 至少两个音节：一个音节对得上的字太多（`bao` 能对上几十个字），`bang`、`long` 这样一个音节的英文词也会对上到处都有的汉字。
  只认完整的音节，所以敲到 `baog` 还找不到"报告"。
- 单独一个 `a`、`o`、`e` 接在别的音节后面时要写隔音符号，和拼音的正词法一样（`tian'e` 是"天鹅"）；不然 `lie`
  会被拆成 li + e。别的以元音开头的音节不用：`xian` 找得到"西安"，`fangan` 既找到"方案"（fang'an）也找到"反感"（fan'gan）。
- 首字母至少 3 个字母，而且只看标题。两个字母对上的太多（`bg` 对得上"不过""不管""宾馆"……），正文又长又多，
  3 个字母也几乎每段都有（`zgr` 对得上每一个"这个人"）。标题短，也是人最记得住的。
- 几个关键词都是字母、又没有哪段会话把它们全都原样找到时，再把它们连起来当一串拼音试一次，空格就是音节的分界：
  `bao gao` 就是这样找到"报告"的。

智狐不给每段会话预先存好拼音（几千段长会话的拼音比原文还占地方），而是反过来，把关键词变成一个正则：每个音节换成
"读这个音的所有汉字"组成的字符集合，`baogao` 变成 `[包保报宝抱…][高告搞稿糕…]`。正则在 C 里跑，和"隔字包含"一样快，
1000 万字也只要几十毫秒。一串字母有几种拆法时（`xian` 是"先"也是"西安"），每种拆法都是这个正则里的一条岔路。
读音来自 Unicode 的汉字数据库 Unihan：[harness/search_pinyin.txt](../../harness/search_pinyin.txt) 是一张 4 万多个字的表（155 KB），
由 [tests/make_pinyin.py](../../tests/make_pinyin.py) 生成一次（见[第三方数据](../../README.zh-CN.md#第三方数据)），第一次需要按拼音找的时候才读进来。
怎么对在 [harness/search_pinyin.py](../../harness/search_pinyin.py) 里。

页面上的搜索结果里标出来的位置是服务器算好的。这里有个容易踩的坑：浏览器里的字符串按 UTF-16 计数，
一个表情符号占两格，而 Python 里只占一格，所以服务器发给页面之前要把位置换算一遍，否则文字里一有表情，
后面标的位置就全偏了。
